# Планирование и методика моделирования

## Методика

### Порядок действий

Цель — построить или изменить модель. **Начать с подходящего примера или рецепта и адаптировать его под задачу.** Сигнатуры, docstrings и справку SDK уточнять через `sdk.py` ([документация и сигнатуры API](setup-sdk.md#документация-и-сигнатуры-api)) по мере работы.

1. Подключиться через `ksapi.GetKompas()` к существующей API-сессии. Нужный документ найти по **абсолютному пути** через `GetDocuments().GetItemByFilePath(path)`; если он ещё не открыт — открыть при помощи `Open`. Проверить тип и `GetFullPath()`. Уже открытый документ не переоткрывать, не заменять дисковой версией и не закрывать. Для новой модели создать собственный документ.
2. Выбрать дерево новой детали или минимальную правку существующей: **параметр → эскиз → операция → вхождение → сопряжения**. Не пересоздавать модель ради одного изменения. Перед сложной правкой сохранить только нужное исходное состояние.
3. Написать макрос на основе подходящего раздела [рецептов](workflow.md#рецепты-для-компас-3d-на-python) или [примера](examples.md#каталог-готовых-примеров): задать размеры, геометрию и последовательность операций. Сигнатуры и docstrings уточнять через [`sdk.py doc`](setup-sdk.md#документация-и-сигнатуры-api); семантику недостающих вызовов — в SDK.
4. Выполнить макрос в КОМПАС. **Один процесс обращается к CAD во время изменения модели**; не запускать параллельно даже API-инспектор. Собственные временные документы и редактирование эскиза закрывать в `finally` только при работоспособной сессии ([§24](documents.md#24-закрыть-только-свои-временные-документы)). Один владелец закрывает каждый документ не более одного раза; функция с заимствованным handle не закрывает и не переоткрывает его. После смены топологии/Undo заново получать используемые грани. У выходных кортежей проверять статус; setters могут возвращать `None`.
5. Обновить затронутую модель (`RebuildModel` / `CompleteRebuildDocument` по ситуации). Проверить результат в КОМПАС: `GetObjectError()` у затронутой операции (при сомнении — обход дерева, [§25](validation.md#25-проверить-ошибки-дерева-и-опору-эскиза)); один нужный геометрический признак (тело, габарит, отверстие). `Update=True` и одно тело сами по себе не доказывают исправность дерева. Сохранить в абсолютный путь, если это входит в задачу. Не перезаписывать чужие файлы без основания; достаточно статуса сохранения и наличия файла, **без обязательного reopen**. Сообщить результат и закончить.

Для знакомой операции обычно достаточно рабочего кода. Примеры полезны при выборе реализации; `sdk.py` и SDK — при вопросах о сигнатуре, маршалинге, поведении или ошибке. Читать столько, сколько помогает следующему действию, без обязательного обхода всех источников. Рискованный неизвестный режим сначала опробовать в собственном временном документе; после обрыва API не повторять запись вслепую.

### Как спланировать модель детали

**От общего к частному:** разобрать форму → выбрать основание и базы → построить основной объём → добавить/удалить материал → повторить элементы → обработать края. Это методика выбора дерева, не единственный правильный порядок. Для существующей модели сохранить её замысел и изменить нужную ветвь, а не проектировать всё заново.

Перед кодом кратко определить:

1. **Геометрия и назначение.** Выделить основные объёмы, отверстия, пазы, посадки и симметрии. По чертежу учитывать виды, разрезы и размеры; не угадывать скрытую форму по одной проекции. Существенные недостающие размеры уточнять, допустимые предположения обозначать.
2. **Основание.** Выбрать конструктивно главный элемент, от которого удобно добавлять/вычитать материал и задавать остальные размеры. Самый крупный объём — частый, но не обязательный выбор.
3. **Базы и ориентация.** Разместить начало координат, главную ось и плоскость первого эскиза по симметрии, монтажным/измерительным базам и удобству дальнейших операций. Предпочитать устойчивые базовые/смещённые плоскости и оси; грань использовать, когда нужна именно связь с ней. Не опирать важные элементы на случайные рёбра скруглений.
4. **Замысел изменений (design intent).** Решить, что должно оставаться соосным, симметричным, равноудалённым или на заданном расстоянии от края. Отверстие «по центру» и «в 10 мм от края» — разные зависимости. По возможности определять эскизы размерами и геометрическими связями без переопределения. Python-переменная и координаты, вычисленные генератором, сами по себе не создают редактируемую зависимость внутри КОМПАС; не выдавать их за полную параметризацию.
5. **Основной объём и конструктивные элементы.** Выбрать операции по форме ниже; затем добавить выступы, рёбра, отверстия и вырезы. Разделять элементы по смыслу и будущим изменениям, а не объединять всё в один сложный эскиз ради меньшего числа операций.
6. **Повторения и завершение.** Использовать массивы/зеркало для конструктивно связанных повторов. Мелкие фаски и скругления обычно делать поздно, чтобы не усложнять опоры. Оболочку, уклоны и формообразующие скругления ставить там, где они правильно задают толщину и переходы; правило «все скругления в конце» не абсолютное.
7. **Результат.** Проверить успешность построения и один итоговый признак, например объём из условия. Само требование параметрической модели не означает обязательного теста изменения размеров; он нужен только по отдельному запросу или при диагностике.

### Как выбрать операцию

- Постоянное сечение вдоль прямой — **выдавливание**; осесимметричный профиль — **вращение**.
- Карман, паз, простой вырез — **вырез выдавливанием**; кольцевая канавка — **вырез вращением**. Для отверстия с собственными параметрами/типом — родная операция **Holes3D** ([§31](features.md#31-родное-отверстие-а-не-окружность-вырез) рецептов).
- Профиль вдоль траектории — **кинематическая операция**; переход между несколькими профилями — **элемент по сечениям**.
- Регулярный повтор — **массив операций**; симметричный элемент — **зеркало**. Повтор тел выбирать только когда нужны отдельные тела, не вместо массива отверстий.
- Тонкостенная полость — **оболочка**; скосы и плавные переходы краёв — **фаски/скругления**.

Для нетривиальной новой детали достаточно одной строки предполагаемого дерева, без отдельного документа и согласования каждого шага. Например, фланец: **вращение ступенчатого профиля (основание + ступица) → центральное отверстие → одно крепёжное отверстие → круговой массив → фаски**. Два выдавливания вместо вращения тоже допустимы: выбирать по удобству размеров и редактирования, не минимизировать число операций любой ценой. Для простой правки отдельный план не нужен.

### Размерная модель, а не замороженный чертёж

Если требуется параметрическая редактируемая модель, задавать конструктивные зависимости **внутри КОМПАС**: совпадение концов, горизонтальность/вертикальность, касательность, равенство, симметрию и управляющие размеры. Фиксировать только необходимую базу; не фиксировать оба конца каждого отрезка ради `WellConstrained`. Нулевые степени свободы, Python-переменные и точные начальные координаты не доказывают сохранение замысла при редактировании. Декоративный размер без управляющей связи тоже не доказательство. `IDimensionText.SetNominalValue()` меняет отображаемый текст, а не геометрию; не использовать его как механизм параметрического изменения.

Параметрическую модель строить с нативными связями и размерами, но **не добавлять пробные изменения размеров в каждое решение**. Тест изменения/восстановления нужен только по отдельному запросу на проверку редактируемости или при диагностике конкретной проблемы. Тогда менять нативный размер и проверять фактическую геометрию; перегенерация профиля Python-кодом не считается этим тестом. Неудачу API не маскировать тотальной фиксацией. Не заявлять проведённый тест редактируемости, если его не выполняли.

Общий пример: [16_dimension_driven_sketch.py](../examples/16_dimension_driven_sketch.py), [маршрут API](sketches.md#размерные-зависимости-эскиза). Существующий размер менять **вне `BeginEdit`**: `ksapi.IFeature(sketch).GetVariableByName(False, True, name)` → `SetExpression(...)` и `SetValue(...)` → `doc3d.CompleteRebuildDocument()` → проверить B-rep. Не использовать `view.GetDimensionVariable(dim)` временного 2D-фрагмента для изменения геометрии: новое значение и успешный rebuild не гарантируют её изменения. `UpdateVariables()` применяет внешние переменные, не является универсальным solver-вызовом. Объекты drawing после нового `BeginEdit` получать заново через `fragment.GetObjectById(id)`. Наличие переменной с новым значением без изменения геометрии не считать успехом. Это правило одинаково для линейных и радиальных размеров: не возвращаться к маршруту через fragment и не подбирать цепочки rebuild. При отказе маршрута через `IFeature` сохранить текущую деталь и сообщить конкретное расхождение, а не переключаться на другой размер ради успешного теста.

### Координаты эскиза и направление операции

Не отождествлять имена плоскостей с привычной экранной ориентацией. Для незнакомой опоры получить `ISketch.GetPoint3D(u, v, 0, 0, 0)` для `(0,0)`, `(1,0)`, `(0,1)`, проверить статус каждого выходного кортежа и вывести локальные оси/нормаль. Для наклонной грани использовать проекцию и обратное преобразование. Это короткая проверка системы координат, не повод строить отдельную пробную деталь для каждого знакомого эскиза.

Направление операции и активная сторона глубины — разные настройки: при обратном направлении настраивать соответствующую сторону `SetSideParameters(False, ...)`. Для нового маршрута подтвердить вход, дно/выход по реальным поверхностям; `Update()` и значение глубины в setter не доказывают сквозной вырез. Не делать обязательным `GetSideParameters()`, если его output-marshalling не работает в нативном KsAPI: это ограничение binding, а не основание пропустить геометрическую проверку.

То же для любой операции с выбором стороны — вырез, смещённая плоскость, оболочка, фаска/скругление, зеркало, знак сопряжения: до вызова прочитать опору (нормаль, габарит), после построения сверить фактическое изменение. Успешный `Update` и «правильное» имя плоскости сторону не доказывают. При расхождении остановиться и сообщить измеренное против ожидаемого, а не менять знак перебором.
