# Нативный KsAPI: справочник рабочего процесса

Это справочник для диагностики и неподдержанных примерами случаев. Для обычной задачи использовать известный код и приступать к выполнению; если реализации не хватает — открыть нужный [рецепт](recipes.md). Проверенный маршрут использовать без повторной квалификации. Чтение этого файла, scratch-проба, инспекция SDK и загрузка базы не являются обязательным прологом. Объём проверок — по риску, как в [SKILL.md](../SKILL.md); подробные отчёты о live-прогонах ниже описывают регрессию, а не обязательный аудит каждой правки.

## Подготовка базы документации

Из каталога установленного скилла, с установленным SDK и локальным Python 3.11+; исходный репозиторий не требуется. Для другой установки замените путь в `cd`:

```bash
cd ~/.cursor/skills/kompass-3d-skill
export LD_LIBRARY_PATH="/opt/ascon/kompas3d-v25/Bin${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
export PYTHONPATH="/opt/ascon/kompas3d-v25/Bin${PYTHONPATH:+:$PYTHONPATH}"
export UV_OFFLINE=1
export UV_PYTHON_DOWNLOADS=never
uv run --script scripts/prepare/prepare_docs.py
uv run --script scripts/prepare/prepare_stubs.py
```

Подготовка читает официальную WebHelp и метаданные установленного SDK, не импортирует `ksapi`, не запускает CAD и не использует сеть. `--help` обоих скриптов описывает выбор установки и выходов. Документация и SQLite FTS5-индекс находятся в `.cache/kompas-sdk-docs`, стабы с подробными docstrings и отчёт типизации — в `.cache/kompas-stubs`; оба каталога расположены внутри установленного скилла. IDE использует стабы, runtime — исходные установленные модули. Manifest фиксирует источники, хеши и фактические счётчики; отчёт стабов перечисляет неизвестные типы и конфликты.

При переносе скилла копировать подготовленный кэш вместе с ним. Другой индекс указать через `sdk.py --docs /path/to/docs` или `KOMPAS_SDK_DOCS`. Если индекса нет, инструмент завершится с указанием команды подготовки, ничего не скачивая.

`llm/pages.jsonl` — переносимый корпус, `llm/api_objects/<section>/` — читаемая документация интерфейсов, `index.sqlite3` — индекс и навигация. По умолчанию поиск использует **нативный KsAPI**, Windows API7/API5 доступны явно через `--section`. Поиск регистронезависимый, все слова/префиксы должны совпасть; русский и английский варианты при необходимости искать отдельно. `page ISketch.BeginEdit` переходит от символа к справке, `toc ISketch` показывает родителей/детей, `links ISketch.BeginEdit` — ссылки. Полный ключ страницы устраняет неоднозначность коротких ID; неоднозначные запросы не выбирают первую страницу молча.

Исходный подход к конвертации: [dwnmf/kompas_3d_api](https://github.com/dwnmf/kompas_3d_api). Официальные входы: `/opt/ascon/kompas3d-v25/SDK/Help/KOMPAS_SDK_ru-RU.zip`, `SDK/KsAPIC/C/Include/KsAPIC.json` и локальная Python-обёртка. Документация SDK генерируется локально, не хранится в исходниках скилла.

## Чтение локальной обёртки

```bash
SDK=scripts/sdk.py
python3 "$SDK" inspect IKompasDocument3D.GetTopPart IPart.GetModelContainer \
  ISketch.BeginEdit IExtrusion.SetProfiles --source
python3 "$SDK" inspect IExtrusion --match 'side'
python3 "$SDK" page ISketch.BeginEdit ISketch.EndEdit IExtrusions.Add
python3 "$SDK" toc ISketch
python3 "$SDK" links ISketch.BeginEdit
```

Поля вывода:

- `signature` — объявление Python с `self`; при вызове связанного метода `self` не передаётся;
- `symbol` — фактический владелец объявления, в том числе базовый класс;
- `path`, `line`, `end_line` — источник для проверки;
- `constructed_interfaces` — интерфейсы, конструкторы которых встречаются в теле метода, **не гарантированный тип результата**;
- `returns_value` — есть ли явный `return` со значением; это не классификатор статуса успеха;
- `source` — тело метода при `--source`, включая преобразования массивов и выходных параметров.

`inspect IExtrusion` перечисляет компактные сигнатуры, включая наследуемые методы; `--match` фильтрует их по имени. Детальное тело запрашивать для конкретного метода через `--source`. Несколько символов в `inspect` разбираются за один проход AST, несколько ID в `page` — за один проход базы. Ошибочные имена не скрывают остальные результаты пакета; общий код завершения при любой ошибке — `1`.

`local` ищет по именам объявлений, `constants` — по именам и русским комментариям. `local` и `search` возвращают `next_offset` для продолжения через `--offset`; `constants` ограничивается `--limit`. Не повторять уже полученные данные. `verify --brief` возвращает количество проверенных имён и отсутствующие символы без повторной выгрузки объявлений.

## Отличия от Windows-справки

- Документированный `IPart7` на проверенной установке представлен классом `IPart`: это видно в теле `IKompasDocument3D.GetTopPart`. Не заменять все имена с суффиксом `7` автоматически.
- Свойство `ModelContainer` представлено `IPart.GetModelContainer()`. Другие свойства могут иметь `Get…`, `Set…`, `Is…` и аргументы — смотреть реальное объявление.
- `ksapi.IKompasDocument3D(doc)` или `ksapi.IDrawingContainer(view)` запрашивает другой интерфейс того же объекта. Вызов `GetTopPart()` или `GetModelContainer()` получает другой объект. Эти переходы не взаимозаменяемы.
- `GetReference(None)` превращается в нулевую ссылку. Это реализация маршалинга, а не разрешение передавать `None` в любой аргумент.
- Методы с выходными параметрами могут требовать начальных значений и возвращать кортеж. Например, локальный `ISketch.GetPoint3D` требует `xIn, yIn, xOut, yOut, zOut` и возвращает статус вместе с координатами.
- Константы обоих модулей находятся в классе `constants`: обычные импорты — `from constants import constants as c` и `from constants3d import constants as c3d`.

## Существующее состояние и минимальная правка

Для существующей модели первым шагом является чтение состояния, не новый генератор. Нормализовать абсолютный путь, получить `documents = app.GetDocuments()`, затем **`documents.GetItemByFilePath(path)` до любого `Open`**. Если документ уже открыт, проверить `GetDocumentType()`/`GetFullPath()` и работать с его текущим состоянием. Не переоткрывать, не закрывать и не заменять дисковой версией dirty-документ пользователя. При отсутствии документа открыть по абсолютному пути и сразу зарегистрировать собственный handle; не определять ownership по имени вкладки или активности.

До записи достаточно короткого контракта **add / change / remove / preserve** и исходных значений нужных объектов/зависимостей. Выбрать минимальный уровень: параметр → эскиз → feature → компонент/вхождение → mates. Метаданные, appearance, слои/видимость и pose — самостоятельные маршруты без геометрической генерации. Совместное скрытие не требует подсборки (§26); pose с mates требует solver/readback (§27). Смена одной детали не обосновывает повторную вставку всех компонентов и создание всех сопряжений. См. [recipes, §§28–30](recipes.md) и [самостоятельный scratch demo](../examples/incremental_edit.py).

Идентифицировать вхождение по пути/стабильному ID, функциональные faces — по геометрии/размеру/базе, не порядковому номеру. После rebuild, Undo/Redo и топологического изменения заново получать ссылки на тела/грани/рёбра. Даже адресная замена компонента **не гарантирует сохранение mates**: проверить пострадавшие references, адресно перепривязать ограничения и доказать preserve-контракт.

### Владение, reuse и проверки

- **Один CAD writer.** У каждого тяжёлого расчёта/import/render один владелец; передать frozen inputs и revision, не запускать дублирующий расчёт. Superseded результаты не применять. Явного ownership и короткой записи этапов достаточно, отдельный orchestration framework не нужен.
- **Reuse по semantic hash**, не `exists()`/mtime: исходники, параметры, recipe/backend/SDK и зависимости. Геометрия, placement, проверка и presentation имеют отдельные ключи; результат проверки также зависит от допусков, предпосылок, алгоритма и его версии. Инвалидировать затронутые зависимости, не всё дерево по умолчанию.
- После логической правки проверить статус, ошибку затронутой операции и простой признак нужного результата. Функциональные поверхности, зазоры и зависимости проверять адресно при соответствующем риске/требовании; для цвета и видимости геометрический контроль не нужен. Дорогую проверку начинать с аналитики/AABB, затем переходить к нужным парам/faces и exact narrowphase. Не импортировать одну геометрию повторно ради metadata.
- **Полный аудит — не условие каждого сохранения.** Рекурсивное дерево, число листьев сборки, матрицы всех вхождений, ground, слои и все живые mates нужны для регрессии, диагностики с неясной областью сбоя или явной приёмки всей сборки. В обычной работе проверять затронутую часть. Motion-test — только по задаче/риску; выполнять на собственной копии, если он нарушает pose пользователя.
- Регистрировать новый документ сразу после `AddWithDefaultSettings`/нового `Open`, до `GetTopPart`. `new_part(app, name, owned=owned)`, `close_owned(owned)` и `feature_errors(part)` в [basic_part.py](../examples/basic_part.py) служат основой; переносить нужные реализации в самостоятельный макрос, **не импортировать проектные scripts**. В `finally` закрывать только собственные временные документы; cleanup не является откатом.
- Для пробы связанной детали копировать файл **до открытия**, затем открыть копию. Это не снимок несохранённых изменений исходного документа. `SaveAs` связанной детали может открыть модальный запрос переназначения ссылок даже при read-only открытии; остановить API и попросить выбрать «Оставить ссылки без изменения». `SaveAs` — не transaction и не pack: внешние зависимости не становятся автоматически переносимыми. Если обещана переносимость, отдельно проверить ссылки и relocate/reopen на собственной копии.

Сохранение — после проверки нужного результата; не сохранять неудачный результат поверх рабочего. Для обычного сохранения проверить статус и наличие файла, без reopen. Если задача — сохранность параметров/ссылок или переносимость, проверить reopen на собственной копии, не закрывая dirty-документ пользователя. Экспорт/рендер — отдельные результаты по запросу. Перед custom UI проверить **реально установленную платформу/capability и штатный инструмент**; наличие панели, enum или Windows-примера не доказывает работающий Linux callback/playback.

При задаче на производительность измерять `time.perf_counter()` отдельно для edit/build, rebuild, check, save и запрошенных export/render; сохранять revision и cache hit/miss. Для обычной правки эти замеры не нужны. Benchmark — одинаковая правка на копиях одной исходной ревизии с теми же проверками и обозначенным cold/warm cache. Число операций/RPC — структурная метрика, не время и не доказанный speedup.

## Последовательности исследования

Цепочка «новая деталь → эскиз XOY → кривые → выдавливание профиля с отверстием → одно твёрдое тело → сохранение» выполнена через нативный KsAPI v25 в Linux при построении детали. Это свидетельство для конкретной установки и набора параметров, не гарантия всех сочетаний операций. Для новой детали начинать с этой цепочки; для существующей — с минимальной правки выше. Для новой операции исследовать только неизвестные звенья. **Snippet вставки в §16 статически сверён, но его конкретный прогон не выполнен; mates и motion из §27 проверены ранее отдельно.** Не переносить статус одной пробы на весь сборочный API.

### Новый документ и верхний компонент

1. `IApplication.GetDocuments()` → `IDocuments`.
2. `IDocuments.AddWithDefaultSettings(documentType, visible)` → общий `IKompasDocument`; тип детали/сборки найти среди констант `ksDocumentPart`/`ksDocumentAssembly`.
3. `ksapi.IKompasDocument3D(doc)` → интерфейс 3D-документа.
4. `IKompasDocument3D.GetTopPart()` → `IPart`.
5. `IPart.GetModelContainer()` → `IModelContainer`.

Проверять непустые ссылки на каждом этапе. Для существующей модели сначала подтвердить тип и полный путь документа.

### Эскиз и геометрия

1. `IPart.GetDefaultObject(objectType)` — получить опорную геометрию; для базовой плоскости найти `o3d_planeXOY`, `o3d_planeXOZ` или `o3d_planeYOZ`.
2. `IModelContainer.GetSketchs()` → `ISketchs`; `ISketchs.Add()` → `ISketch`.
3. `ISketch.SetPlane(plane)`, затем `ISketch.BeginEdit(readOnly)` → `IFragmentDocument`.
4. Проверить у `IFragmentDocument` доступ к видам; получить активный `IView` и запросить `IDrawingContainer`.
5. Получить нужные коллекции и создать контур. Проверить параметры геометрии, `Update()` и замкнутость контура.
6. Завершить `ISketch.EndEdit()` до создания операции. В макросе обеспечить завершение редактирования при исключении через `finally`.

Искать страницы `isketch_beginedit`, `isketch_endedit`, затем методы конкретной геометрии. Для новых плоскостей, проекций и пространственных кривых исследовать отдельные интерфейсы, не подменять их базовыми плоскостями.

### Выдавливание и вырез

1. Прочитать `iextrusions_add`: разрешены `o3d_bossExtrusion` и `o3d_cutExtrusion`.
2. `IModelContainer.GetExtrusions()` → `IExtrusions`; `IExtrusions.Add(extrusionType)` → `IExtrusion`.
3. В Linux `IExtrusion.SetProfiles(profiles)` принимает коллекцию ссылок через `ToObjectReferenceVector`. Документационный поиск по слову `Profile` может показывать другой интерфейс, например `IExtrusion1`; проверить владельца перед переносом.
4. Проверить `IExtrusion.SetDirection` и константы направления; для сторон операции изучить `SetSideParameters(self, normal, extrusionType, depth, draftValue, draftOutward, depthObject)`.
5. Константу способа ограничения, допустимость `depthObject` и поведение первой операции брать из справки. `normal` задаёт сторону, `extrusionType` здесь — способ ограничения, не тип операции из `IExtrusions.Add`. Для выреза из нижней XOY в материал Z>0 проверены `SetDirection(c3d.dtReverse)` и `SetSideParameters(False, ...)`; направление и сторона глубины задаются согласованно.
6. Вызвать унаследованный `IModelObject.Update()`, проверить его результат; выполнить `IPart.RebuildModel(redraw)`.
7. Проверить фактические глубину, направление, число тел и габариты через доступные getters. Для выреза проверить изменение геометрии, а не только наличие операции в дереве.

### Минимальное построение и контроль твёрдого тела

Проверенный вариант для плоского профиля: `GetSketchs().Add()` → `SetPlane(part.GetDefaultObject(c3d.o3d_planeXOY))` → `sketch.Update()` → `BeginEdit(False)` → активный вид фрагмента → `ksapi.IDrawingContainer(view)` → геометрия → `EndEdit()` → выдавливание. Круг внутри внешнего замкнутого контура в этом варианте дал сквозное отверстие без отдельного выреза.

Выдавливание: `model.GetExtrusions().Add(c3d.o3d_bossExtrusion)` → `SetProfiles([sketch])` → `SetDirection(c3d.dtNormal)` → `SetSideParameters(True, c3d.etBlind, depth, 0.0, False, None)` → `Update()` → `part.RebuildModel(True)`. Здесь `None` использован для ограничителя при заданной глубине; это не универсальное разрешение для произвольного режима.

Контроль: `ksapi.IFeature(extrusion).GetResultBodies()` возвращает список; проверить число тел, `body.IsSolid()` и `body.GetGabarit(0, 0, 0, 0, 0, 0)`. Последний возвращает `(status, xmin, ymin, zmin, xmax, ymax, zmax)`. `extrusion.GetDepth(True)` проверяет параметр глубины, не наличие выреза в теле. `doc.SaveAs(absolute_path)` возвращает статус. Для размеров и толщины простого выдавливания не требуется исследовать массу и инерцию.

В `examples/basic_part.py` добавлен `verify_cylindrical_walls`: `ksapi.IFeature(part).GetModelObjects([c3d.o3d_face])` → `ksapi.IFace(obj)` → `IsCylinder()` → `GetRadius()` и `GetLimitingEdges()`. Для круговых рёбер `GetMathCurve().GetGabarit(...)` даёт центр, радиус и уровни Z двух границ стенки. Они сопоставляются с ожидаемыми стенками кольца и отверстий, включая глухую глубину; проверка выполняется до сохранения. Это ограниченный контроль простых цилиндров вдоль Z без скруглений и разбиений. Цепочка подтверждена в CAD 20.10.2026: кольцо, четыре сквозных отверстия и глухие отверстия глубиной 3 мм. Ранний вырез давал `Update=True` без отверстий: для нижнего эскиза XOY и материала Z>0 нужна пара `dtReverse` + `SetSideParameters(False, ...)`. Итоговое тело проверяется через `IFeature(part)`, не через пустой список результата операции выреза. Готовые самостоятельные примеры и JPEG — в [каталоге рецептов](recipes.md).

### Кривые: сначала один элемент

- `ICircle` задаёт центр через `SetXc`/`SetYc`, а не `SetX`/`SetY`. Оба набора методов существуют в `ICircle`, но наличие имени не означает нужную семантику параметра центра. Проверка существования имён такую ошибку не обнаружит.
- `IArc.SetDirection(True)` — по часовой стрелке, `False` — против; углы `SetAngle1/SetAngle2` задаются в градусах. Готовая функция с проверкой длины и внутренней точки — [рецепт 17](recipes.md). Универсальное сопряжение с обрезкой и ограничения `ICurve2D.CouplingCurveCurve` — рецепт 18; числовой результат этого метода не является готовыми объектами кривых.
- `drawing.GetBeziers().Add()` → `IBezier`. Для открытой составной кубической кривой: `SetClosed(False)`, затем `AddPoint(index, x, y, x_left, y_left, x_right, y_right)` для каждого узла; `left`/`right` — абсолютные координаты управляющих точек. `AddPoint` возвращает кортеж, проверять его статус. После задания узлов — `Update()`.
- Эта цепочка Безье выполнена для гладкой аппроксимации аналитического профиля. Её точность зависит от построения управляющих точек и шага, не от одного факта использования Безье.
- В одной пробе `INurbs.SetNurbsParams` с составным кубическим профилем прошёл создание, но контроль расстояния до расчётных точек выявил расхождение около 0,000748 мм. Причина не установлена: это не доказательство дефекта всех NURBS. Если используются полюса, веса и узлы, проверить один короткий участок до генерации всей модели.
- `obj.GetCurve2D().PointOn(parameter, 0, 0)` возвращает статус и координаты; параметры брать из `GetParamMin()`/`GetParamMax()`. `GetDistanceToPoint(x, y)` измеряет расстояние до фактической кривой. Начать с концов и нескольких внутренних точек представительного участка; увеличить выборку только при необходимости.
- Для повторяющегося профиля считать ошибки аппроксимации локально; в API проверить представление одного участка, стыки и итоговое тело. Выборочная проверка — не доказательство максимальной ошибки между точками. Допуск выбирать из задачи и масштаба геометрии, не ужесточать произвольно до нанометров.

### Сборки

В [рецептах, §16](recipes.md) дана статически сверенная цепочка вставки внешней детали: документ `ksDocumentAssembly` → верхний компонент → `GetParts().AddFromFile(...)` → `GetPlacement()` → `UpdatePlacement(True)`. **Именно этот snippet не подтверждён нативным прогоном.** Это не утверждение «сборки никогда не выполнялись»: [§27](recipes.md) содержит ранее проверенные mates, сохранение/reopen, матрицы и motion на копии сборки. Точка входа сопряжений — `IKompasDocument3D.GetMateConstraints`; перемещение ЛСК не заменяет сопряжение. В обычной правке проверять путь и изменяемое вхождение/сопряжение; полный набор листьев, матриц, ground, слоёв и mates относится к аудиту всей сборки. Движение проверять, когда оно входит в задачу. Один статус `Update` не заменяет readback; в прежних пробах `False` встречался при применённом состоянии, но это не разрешение игнорировать сбой. Последующая отдельная live-проба ниже подтвердила Undo/Redo переноса и правок mates на простой сборке; исходный snippet со строгим `require(UpdatePlacement(...))` остаётся непригодным для наблюдавшегося `False` при применённом состоянии.

## Undo: однодокументная группа, не транзакция

Подробные рецепты — [§§28–30](recipes.md), воспроизводимый самостоятельный пример — [incremental_edit.py](../examples/incremental_edit.py). Перед группой подтвердить целевой active document/frame, `IsEnableUndo()` и отсутствие чужой открытой группы через `IsUndoContainer()`. Не присваивать чужую группу. Открытую собственным кодом группу закрыть через `SetUndoContainer(False)` в `finally`; **закрытие не отменяет выполненные изменения**, exception также не откатывает их.

Живая квалификация Linux v25, 20 октября 2026:

- `c.ksCMEditUndo = 57643`, `c.ksCMEditRedo = 57644`. `prUndo=10211`/`prRedo=10212` — другие константы, не проверенный здесь маршрут.
- Синхронный вызов — `doc.GetDocumentFrame().ExecuteKompasCommand(command, False)`. До него проверить целевой документ/frame и `IsKompasCommandEnable(command)`; после — фактическую геометрию, не только возврат команды. Заново получить topology references после Undo/Redo.
- `SetUndoContainer` и `SetEnableUndo` возвращают **`None`**: читать состояние через `IsUndoContainer()` / `IsEnableUndo()`, не проверять setter как bool. `ClearUndo()` возвращает **bool**.
- **4 scratch-part сценария passed**: одиночная глубина `10→15`, Undo `→10`, Redo `→15`; группа `20→25` отменяется одним шагом к `15`, Redo возвращает `25`; exception внутри группы оставляет глубину `18` после `finally`, только явный Undo возвращает `10`; пустая группа сохраняет `12` и прежнюю доступность Undo — отмена намеренно не вызывалась. `SetEnableUndo(False/True)` и очистка undo/redo через `ClearUndo` проверены только в scratch.
- Первая assembly-placement проба остановилась на `SetOrigin(30,0,0)=True`, `UpdatePlacement(True)=False`; это исторический результат, не доказательство отсутствия Undo. Все пять документов той пробы закрыты.
- **Повторная изолированная live-квалификация: 4 сборочных сценария passed.** Два вхождения собственного нативного блока, одно ground. Группа переносов X `0→30→40`, один Undo `→0`, Redo `→40`; `UpdatePlacement(True)` оба раза `False`, но непосредственная матрица и успешный `RebuildModel(True)` подтверждали перенос. Группа создания двух coincidence + одного distance: число живых mates `0→3→Undo 0→Redo 3`. Параметр distance `0→7→12` перемещал вхождение по Z; Undo вернул параметр/матрицу, Redo восстановил. Удаление distance: `3→2→Undo 3→Redo 2`.
- После каждого Undo/Redo заново получены объекты, сравнены полные матрицы всех вхождений с допуском `1e-6`, ground, источники/твёрдые тела/габариты, типы/параметры/базы mates и нулевые ошибки полного дерева. Это квалификация **этого простого fixture**, не всех placements/mates, topology replacement, 2D или multi-doc Undo. В начале/конце документов `0`; собственные документы закрыты, временные файлы удалены, SHA256 исходного блока не изменился, API не оборвался. Причина возврата `False` не установлена; без readback и проверок игнорировать его нельзя.

Пустая группа не доказывает появления нового undo-step: доступная команда может относиться к предыдущей пользовательской операции. Не выполнять Undo без известной завершённой изменяющей группы и квалификации данного типа правки. После неизвестного исхода вызова/обрыва **нет автоматического Undo**: остановить запись и проверить состояние; закрытие собственной scratch-копии без сохранения не является откатом пользовательского документа или файлов. Не очищать и не отключать историю по умолчанию. Группа не обеспечивает multi-doc atomicity, rollback сохранённых файлов или упаковку ссылок; `SaveAs` также этого не обеспечивает.

## Размерные зависимости эскиза: доступность и квалификация

Следующие имена проверены по локальной Linux-обёртке; **наличие методов не означает успешную live-квалификацию произвольного эскиза**.

- `IDrawingObject.NewConstraint()` → `IParametricConstraint`: до `Create()` задать `SetConstraintType`, `SetPartners([...])` и нужные `SetIndex`/`SetPartnerIndex`; после проверить результат и `IsValid()`. Windows-имя `IParametriticConstraint` и одиночный `Partner` не копировать в Linux. Для изменения уже созданной связи документация описывает удаление/создание; post-create `SetConstraintValue()` не считать доказанным resize-маршрутом.
- Геометрические связи: `ksCMergePoints`, `ksCHorizontal`, `ksCVertical`, `ksCParallel`, `ksCPerpendicular`, `ksCEqualLength`, `ksCEqualRadius`, `ksCTangentTwoCurves`, `ksCSymmetryTwoPoints`, `ksCConcentricity`. Фиксировать минимальную базу, не все вершины.
- Линейные размеры: `ISymbols2DContainer(view).GetLineDimensions().Add()`, координаты выносных линий, `SetOrientation(ksLinDHorizontal/ksLinDVertical/ksLinDParallel)`, `Update()`. Связь с геометрией — `ksCAssociation`; управляющие связи — `ksCFixedDim` / `ksCDimWithVariable`. Точный порядок создания и индексы требуют проверки. `Associate()` может выбрать не ту совпадающую точку: проверять фактических партнёров и результат изменения.
- Для изменения существующего управляющего размера эскиза использовать `ksapi.IFeature(sketch).GetVariableByName(False, True, name)` **вне `BeginEdit`** → `IVariable.SetExpression(...)` и `SetValue(...)` (возвращают `None`) → `doc3d.CompleteRebuildDocument()`. Проверять фактическую геометрию, состояние solver и ошибки операций; восстановить номинал. `view.GetDimensionVariable(dim)` внутри временного 2D-фрагмента на Linux v25 не даёт воспроизводимого изменения геометрии; успешные `UpdateVariables()` и `fragment.CompleteRebuildDocument()` этого не гарантируют. `UpdateVariables()` относится к внешним переменным, не является универсальной заменой solver.
- `IDimensionText.SetNominalValue()` меняет показанный текст, а не геометрию. Декоративная надпись и fully-constrained фиксация не доказывают размерное управление.

**Live Linux v25, уточнение 2026-10-20:** прежний комбинированный маршрут через временный 2D-фрагмент проходил отдельные проверки прямоугольника, но повторные эксперименты на детали 1.1 воспроизвели расхождение: переменная и размерная связь уже 64 / R7, координаты остаются 60 / R6, а rebuild возвращают `True`. Дополнительные rebuild, обновление размера/вида, смена параметрического режима и ожидание не дали универсального исправления. Это локализует отказ до получения новой геометрии эскиза; внутреннюю причину реализации solver/API без исходников не установили.

**Новый воспроизводимый маршрут через `IFeature` вне редактирования** прошёл на десяти новых деталях 1.1 подряд: ширина 60 → 64 → 60 и радиус 6 → 7 → 6, реальные границы/цилиндр B-rep, отверстие сохраняет правый отступ 16 мм, оба эскиза `WellConstrained`, дерево без ошибок. Дополнительно три цикла прошли на копии итоговой `.m3d`, затем сохранение и повторное открытие с проверкой номинальной геометрии. Не квалифицированы произвольные сети и межразмерные выражения. Объекты drawing из завершённого `BeginEdit` не использовать в следующем сеансе; вновь получать через ID в актуальном fragment. Пример: [16_dimension_driven_sketch.py](../examples/16_dimension_driven_sketch.py).

Справка из Windows-кэша объясняет назначение, но её имена и COM return types не определяют Linux-маршалинг. Например, локальные `Save()` / `SaveAs(path)` возвращают `res`, хотя Windows-страницы описывают void Automation methods. Ни `SaveAs`, ни `SaveAsToRasterFormat(path, parameters)` не имеют локального per-call overwrite/silent-флага. `IApplication.SetHideMessage()` задаёт глобальные автоматические ответы и может затронуть ссылки/перестроение; не использовать его как обход коллизий файлов. Правила новых выходных путей и владения документами — в [SKILL.md](../SKILL.md).

## Запуск и проверка результата

Команда запуска API-сервера не зависит от текущего каталога; пути `scripts/…` ниже указаны относительно каталога скилла. `scripts/run.sh` задаёт `LD_LIBRARY_PATH` и `PYTHONPATH` и запускает `uv run --script`, поэтому макрос напрямую импортирует `ksapi` и константы без правки `sys.path`, а зависимости берутся из PEP 723 в начале файла. Для другой установки заменить путь к `Bin` в команде сервера, а для `scripts/run.sh` задать `KOMPAS_BIN`. Принудительный выбор платформы Qt не требуется.

Сначала подключиться через `GetKompas()` к API-сессии пользователя. Если подключения нет, не запускать новый процесс: показать пользователю полную Bash-команду ниже (не наш `.sh`-файл) или предложить запуск агентом и дождаться явного согласия. Запрос на выполнение макроса не считается согласием на запуск КОМПАС.

```bash
# Команда для пользователя, если API-сессия ещё не запущена:
LD_LIBRARY_PATH="/opt/ascon/kompas3d-v25/Bin${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}" \
LC_ALL="${LC_ALL:-C.UTF-8}" \
/opt/ascon/kompas3d-v25/Bin/kKompas -APIServer=10500
# При доступной API-сессии — запуск макроса в другом терминале:
bash scripts/run.sh /absolute/path/to/macro.py
```

`run.sh` не запускает КОМПАС самостоятельно. Макросы также должны использовать только `GetKompas()` и завершаться с понятной ошибкой при отсутствии подключения, без перехода к `OpenKompas()`. Не закрывать и не перезапускать процесс пользователя.

Перед исполнением:

1. Проверить синтаксис макроса через `ast.parse`, без импорта и выполнения.
2. Если есть ошибка, сомнение или существенный вызов вне рецепта, адресно проверить его сигнатуру, константы и ограничения. Не выполнять `inspect`/`verify` для каждого известного вызова перед пробой.
3. Проверить целевую API-сессию и документ. Создание нового документа не должно изменять чужую активную модель.

После исполнения кратко сообщить результат и существенные ограничения; отдельный протокол этапов нужен для диагностики или регрессии, не для каждого макроса. Проверять статус только у методов с соответствующим возвращаемым значением. Присутствие имени в обёртке не доказывает отсутствие ошибки в нативной реализации.

## Полезные внешние реализации

Это источники идей и адресных примеров, не дополнительные обязательные зависимости:

- [IsWaFF/kompas3d-skill](https://github.com/IsWaFF/kompas3d-skill), MIT: нативный `ksapi`, в основном 2D. Полезны примеры размеров, дуг, заливок, поиска наложений и selftest; тонкости направления дуг и экспорта проверять на своей установке. Его distrobox/Xephyr-схему запуска сюда не переносить.
- [kostia-egik/geomwright](https://github.com/kostia-egik/geomwright), MIT: Windows COM, не нативный KsAPI. Полезны [CAD-инварианты](https://github.com/kostia-egik/geomwright/blob/main/CAD_PATTERNS.md): разделение расчёта и построения, чтение конечной геометрии независимо от истории и остановка после неизвестного исхода вызова. Сложные инженерные семейства и проверки сохранения не добавлять в простую задачу без необходимости.
- [SergeySklyarov/Kompas3D-MCP](https://github.com/SergeySklyarov/Kompas3D-MCP): Windows COM/.NET. Полезно различение «вызов вернулся», «геометрия проверена», «сохранение/повторное открытие проверены» и явное перечисление непроверенного. После изменения топологии заново выбирать грани/рёбра; после обрыва соединения не повторять запись до проверки состояния. Его механизм автозапуска/перезапуска не переносить.
- [hymaxo/kompas3d-mcp](https://github.com/hymaxo/kompas3d-mcp), MIT: Windows COM/API5/API7. Полезна [коллекция рецептов](https://github.com/hymaxo/kompas3d-mcp/blob/main/skills/kompas-modeling/references/recipes.md) с входными размерами, ожидаемыми габаритами, числом тел и аналитическим объёмом. Использовать её как источник геометрии и критериев результата, а вызовы адаптировать по нативной обёртке. Объём проверять, когда он нужен для подтверждения внутренней операции, не как обязательный этап каждой задачи.
- [xomyachok-shaolin/kompas-3d-mcp-linux](https://github.com/xomyachok-shaolin/kompas-3d-mcp-linux): нативный C++ KsAPI v24 в Linux. [bridge.cpp](https://github.com/xomyachok-shaolin/kompas-3d-mcp-linux/blob/main/src/bridge.cpp) полезен для поиска цепочек 2D-размеров, штампа и экспорта. Явная лицензия на повторное использование не установлена: код не копировать; его запуск, IPC и threading-схему не переносить.
- [nikitamamay/KompasAPI-01](https://github.com/nikitamamay/KompasAPI-01), MIT: Windows COM-обёртка со stubs и встроенной документацией. Полезны типы и иерархия для поиска понятий, но это не stubs нативного KsAPI и не источник его фактических сигнатур. Не возвращать LSP и COM-зависимости ради этой базы.

Код этих проектов в скилл не скопирован. Даже MIT-код перед переносом требует сохранения уведомлений о лицензии и проверки применимости к нативному API; документация SDK может иметь отдельные права.
